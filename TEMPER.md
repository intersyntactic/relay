# TEMPER.md — is_relay

**Overall verdict:** RECAST (4 of 4 families; no DISSOLVE)
**Struck:** dt-1795440685, families seated: Maxwell + Noether, Carnot, Tesla (Wu disabled). Noether's first launch dropped (DeepInfra stream closed after 122 s, rc 6); its second landed.

## Per-family verdicts
| Family | Verdict | One-line |
|--------|---------|----------|
| Maxwell (Claude) | RECAST | Verified bytes aren't the whole delivery (GitHub's kind is an unsigned header), and both safety types fail at the logbook boundary |
| Carnot (GPT) | RECAST | Delete the relay replay cache. It can ack a duplicate before the original is recorded. Idempotence belongs at durable admission |
| Tesla (Grok) | RECAST | `at` salts away the logbook's identity and a seen set fakes it back. `Coverage` is stripped at the only door out |
| Noether (DeepSeek) | RECAST | GitHub breaks "the entry holds what its translator needs" and has no source key in its body |

## Fatal flaws (deduped, most-severe first)
1. **GitHub's event kind is an unsigned header, and the design records body bytes only.** Raised by all four. The translator can't tell `issues` from `ping`, and a replayer can relabel the header. DISPOSITION: fold. The recorded delivery separates *covered* bytes from *uncovered* context, by type. The relay never filters on uncovered context: GitHub records every HMAC-valid delivery and the translator classifies. Carrying the header into the entry as labelled-unsigned context needs a docking station format change (brief docking-station-9b).
2. **The relay's seen set is a check whose producer lives elsewhere, and it is unsafe.** Raised by all four. Carnot traced a race in teams_relay today: A marks the key seen and awaits the record, B gets 200 from "seen", A's record fails, and B's 200 has already ended Teams' retries, so the event is lost. The producer of "acted on twice" is the reader, and the docking station's contract already makes that impossible: `EventKey`, "what 'not decided twice' compares", chosen by each module. DISPOSITION: fold. Delete the seen set and `ReplayKey` from is_relay. Idempotence is the translator's `EventKey`. GitHub's key is the sha256 of the delivery bytes, because its body has no id. Brief teams-module about the race.
3. **`Coverage` dies at the logbook.** Raised by all four. For Teams the cost is admission, not replay. A captured token lets anyone write a body naming any `from` (Tesla). DISPOSITION: fold. Coverage is a fixed fact of each source, so the source's kind already implies it. State it in the translator contract: a `senderOnly` source's body fields are the token holder's testimony. The docking station may admit on them only under a trust rule the module states, and `addressedTo` and `replyEndpoint` alone are verified. Don't keep an enum that nothing reads.
4. **The `VerifiedDelivery` construction argument contradicts itself.** Raised by Maxwell and Carnot. Noether and Tesla read it as sound. DISPOSITION: fold. `checkBody` returns a verdict without bytes. The relay owns an immutable snapshot of the bytes it read and builds the `VerifiedDelivery` privately.
5. **No overall time budget.** Raised by Carnot and Tesla. A 10 s body read plus a 10 s write exceeds Slack's 3 s, and `Future.timeout` doesn't cancel the work underneath. DISPOSITION: fold. One monotonic budget per source covers read, check and record, plus a cap on concurrent requests.
6. **Dropping `at` was framed as replay protection.** Raised by Maxwell and Carnot. Tesla and Noether wanted it as a requirement instead. DISPOSITION: fold as an optional storage optimisation, not part of correctness: once #2 holds, a duplicate entry costs storage, not a double action. Tesla's point stays true: if anyone ever writes a chain tip as `previous`, logbook-level dedupe is gone, so correctness must not rest on it.
7. **An unsigned Teams activity key lets a token holder get in first and shadow an honest activity** (Tesla). DISPOSITION: named tradeoff. Owner: teams_module. Cost: a holder of a captured token can suppress or replace activities, which is within what that token already allows (forge any body). Mitigation: TLS and short token lifetimes, plus the Fable audit's first question.
8. **Do Teams retries resend byte-identical bodies?** Not measured (Tesla). DISPOSITION: now non-blocking. With #2, it only affects storage. Still worth measuring.
9. **GitHub has no signed time, so a captured, never-delivered body is accepted once** (Tesla). DISPOSITION: named tradeoff. Owner: is_relay. Already-recorded captures are no-ops under the bytes `EventKey`. A capture never delivered to us needs an attacker positioned between GitHub and the relay's TLS.

## What holds
- "The logbook is the only way out": record, then answer. `Written` and `AlreadyRecorded` mean 2xx, anything else 5xx. `/ws` and `onEvent` are gone.
- Header check, then body. Refusal without reading the body (`_refuseUnread`). One deadline for the whole body. Fail closed on missing configuration.
- Teams' sender-only coverage named honestly. Slack's timestamp is inside its HMAC.
- Parsing stays in each source package.

## Disposition
RECAST: fold #1–#6 into DESIGN.md, record #7 and #9 as named tradeoffs, and re-strike (round 2 of ≤3).

## MaxwellMergeSlam's Design Strike

**Verdict:** RECAST

**Summary:** The design treats "the verified bytes" as the unit that crosses the relay. For GitHub, part of what a delivery means (its event kind) lives in an unsigned header. And the design's two safety types, `VerifiedDelivery` and `Coverage`, don't hold at the one boundary that matters, the logbook.

**Producer first:** The relay's in-memory seen set (the "until the docking station agrees" fallback) guards against *a duplicate delivery being acted on twice downstream*. The trigger is external: sources retry, and attackers replay. The PRODUCER is ours. It is the downstream reader acting on an entry without deduping by the source's event key. That producer has to be fixed downstream anyway, because the seen set forgets on restart and on every 5xx. The design admits this ("Downstream dedupes by the source's key. That holds today and stays true under either option"). So the seen set guards an outcome the reader already makes impossible. Delete it: it is a second check on something one key already owns. The `AlreadyRecorded` dedupe from recording only the bytes is the same kind of thing, a saving in logbook growth rather than a safety property, and the doc should say so instead of calling it "replay protection".

**Fatal flaws:**
- **Make "duplicate acted on" impossible at the reader, then drop the relay's seen set** (check whose producer could be removed). See Producer first. The "Replay" section mixes two separate concerns. The first is *authenticity*, the delivery check. The second is *idempotence*, which belongs to the reader and is keyed by the source's own event id (Slack `event_id`, the Teams conversation and activity id, a GitHub body hash). The relay can't own the second, because it restarts and answers 5xx. Say that, and drop the `ReplayKey` machinery from is_relay.
- **The `VerifiedDelivery` construction argument contradicts itself** (unstated assumption; type safety that doesn't hold). "is_relay makes one only inside `Verified`, and a source gets one only by returning it from `checkBody`." If the source returns a `Verified` holding a `VerifiedDelivery`, the source has to be able to construct one, so the constructor is public to every source package and so to anyone. Fix: `checkBody` returns a bytes-free verdict (`Verified`, `Quiet`, `Refused`). The relay pairs `Verified` with the exact bytes *it* read and passed in, and builds the `VerifiedDelivery` itself, privately. Then the bytes recorded are the bytes checked by construction, and no source can substitute different ones.
- **GitHub's event kind is unsigned and the design drops it** (missing failure mode / wrong frame). "Record the verified bytes" assumes the body holds everything a reader needs. For GitHub, `X-GitHub-Event` names what the body is, and the HMAC doesn't cover it. `webhook_gate.dart` itself says a signed `ping` body can be relabelled `issues`. Recording bytes only loses the event kind. Recording bytes plus the header records an attacker-chosen label next to signed content. The record format needs signed content and unsigned context as separate typed parts, so a reader can't treat the label as verified. The same holds for Slack's content type (form or JSON), which slack-module-1e already hit.
- **`Coverage` dies at the logbook boundary** (coupling or dead type). Nothing reads `Coverage` before recording, and the entry "is the same either way". Downstream reads only the logbook, so the one property it most needs, whether this content is authenticated or only its sender is, is never in front of it. Either record it, for example in the kind or a field, or delete the enum. A type that nothing past the boundary can see is decoration.
- **The `at` proposal is weaker than it looks** (wrong frame). Dropping `at` to buy `AlreadyRecorded` dedupe only saves logbook growth, once the reader is idempotent per the first flaw. It still costs a cross-repo format change and the loss of arrival time. Downgrade it from "Proposal" to an optional optimisation, and make the reader's idempotence the actual requirement in the docking-station brief.

**What holds:**
- "The logbook is the only way out", with record-then-answer and `Written`/`AlreadyRecorded` mapped to 2xx and everything else to 5xx. This is right and simple.
- Splitting the check into headers then body, with refusal before the body is read, the whole-body deadline, and refusing without reading the rest. These are proven in teams_relay and are genuinely shared.
- The honest statement that the Teams token doesn't cover the body and no relay design closes that.
- Failing closed on missing configuration. Parsing stays in the source packages.

**If RECAST, what to fold back:**
- Replace the Replay section: the relay owns authenticity only, and idempotence is the reader's, keyed by the source's event key. Remove `ReplayKey` and the seen set from is_relay. The bytes-only body becomes an optional optimisation.
- `checkBody` returns a verdict without bytes. The relay builds `VerifiedDelivery` from the bytes it read.
- Define the recorded delivery as `{signed: bytes, context: {name: value}}` (or a source-declared subset of headers), and say in the type which parts the check covers. This goes to the docking station as a format change alongside, or instead of, the `at` question.
- Carry coverage into the record, or delete `Coverage`.

## CarnotCodeCarver's Design Strike

**Verdict:** RECAST

**Summary:** The shared HTTP-to-logbook boundary holds. The replay design does not: it confuses recording identity with event identity and can acknowledge an event before durable recording. Dissolve the relay replay cache and keep correctness at durable admission. No real engine matches the Carnot cycle; a reviewer's job is to say how far short we are. This design generates avoidable entropy through duplicated state. Dijkstra: "Simplicity is prerequisite for reliability."

**Producer first:** The harms are lost commands, repeated actions, dropped edits, and forged content becoming trusted actions. External retries, captured credentials, and stalled connections are triggers. Our producers are: the relay's early seen marking and duplicate-success response; downstream effects executed more than once; deduplication that collapses distinct events; translators interpreting bytes without the delivery context their gate used; and resource-holding operations that outlive request deadlines. These producers are addressed below. Authentication itself cannot be deleted: Teams submissions and other commands carry content that must cross an untrusted boundary. Source checks remain necessary, but a checked-delivery type must preserve exactly what was checked and must not imply stronger authentication than the protocol provides.

**Fatal flaws:**
- make duplicate user actions impossible: use the docking station's durable, source-scoped EventKey admission as the single decision point, with effects committed atomically or issued through an idempotent effect mechanism; then relay replay checks become unnecessary for correctness. Keep recording attempts safe to repeat. This removes the cache, restart behavior, eviction policy, and format migration from the correctness argument. The existing 'decides once' contract is the right home, but the bundle does not establish its crash-safe connection to effects.
- The transitional seen set can lose an event. Request A marks a key seen, then awaits recording. Request B arrives, sees the key, and receives 200 without a durable record. A subsequently fails or the process crashes. B's successful acknowledgement was false. The supplied Teams relay demonstrates this sequence. Forgetting the key after a 5xx cannot revoke B's 200. Delete duplicate-success responses based on volatile state; acknowledge each accepted delivery only after durable evidence exists.
- A body hash identifies bytes, not necessarily one occurrence. Permanent AlreadyRecorded behavior is safe only where identical authenticated bodies necessarily represent the same event. That invariant is not established for every supported command and webhook shape. Conversely, byte changes can represent one Teams activity. The bundle also contains conflicting Teams identity contracts: the gate distinguishes type and timestamp, while teamsRecordedEvent instructs consumers to use conversation and activity id, which would collapse edits and deletes. Define one source-specific occurrence identity and use it consistently at durable admission.
- GitHub's proposed recorded form discards context used by its gate. The event discriminator comes from an unsigned header, while the logbook receives only body bytes. The downstream translator cannot generally recover the gate's interpretation from that envelope. A replay can also relabel the header. Define a complete interpretation contract: which metadata survives, which fields authenticate the interpretation, and how incompatible payloads are handled. Do not promote the claimed header into an authenticated event kind.
- The VerifiedDelivery construction story does not establish its advertised guarantee. An external source implementation must somehow create the value whose constructor is private to is_relay; that construction authority is unspecified. More fundamentally, a verified Uint8List can change after checking unless ownership is enforced. Make the relay own an immutable snapshot and pair the source's decision with that exact snapshot. A type can enforce passage through the checking interface; it cannot prove that an arbitrary plugin performed valid cryptography.
- The deadline promise lacks an execution and resource model. The supplied defaults permit ten seconds reading plus ten seconds recording, before key retrieval and response completion. Future.timeout stops waiting; it does not itself stop body reading or a write. A timed-out write can still commit while a retry begins. Specify one monotonic request budget, bounded key access and writer operations, cleanup, and limits on concurrent requests and pending writes. Per-request byte caps alone do not bound aggregate memory or cryptographic work.
- Teams senderOnly coverage is acknowledged but its downstream authority remains unspecified. A token holder can invent actor, tenant, activity key, and command content within the accepted token constraints. An allowlist of body fields does not independently authenticate those fields. The translation contract can turn them into authorship, approvals, closes, and reply capabilities. State explicitly which actions accept that bearer-token trust model and carry any verification context they require across the logbook boundary. A Coverage enum discarded before translation supplies no enforceable restriction.

**What holds:**
- Recording before successful acknowledgement and removing in-process dispatch create a clear recovery boundary.
- Raw-byte HMAC verification, early header refusals, and a whole-body deadline are appropriate responsibilities for shared infrastructure.
- The design correctly distinguishes Teams sender authentication from body signatures and identifies Slack signature-digest caching as insufficient for changed retry timestamps.
- The docking station already defines event identity separately from message identity; that is the useful foundation for eliminating relay replay machinery.

**If RECAST, what to fold back:**
- Keep {at, bytes} and remove the transitional seen set. Arrival metadata need not participate in event identity. Changing the envelope can remain an independent storage decision.
- Specify durable admission and effect recovery first, including concurrent duplicates and crashes between admission and action. Retain logbook content deduplication only as an optimization where its occurrence semantics are established.
- Define each source's complete recorded contract, interpretation rules, occurrence key, and trust scope before extracting the common check interface.
- Make RelayServer own the immutable body, request budget, resource bounds, durable write outcome, and final response. Keep source authentication and parsing source-specific.
- Validate the design with failure traces: overlapping duplicates followed by write failure, commit followed by lost acknowledgement, repeated legitimate commands, Teams edits and deletes, relabelled GitHub headers, and deadline expiry during an outstanding write.

## Tesla, the Arc-Prophet's Design Strike

Tesla: "If you want the secrets of the universe, think in energy, frequency and vibration."

**Verdict:** RECAST

**Summary:** The logbook hash is already an idempotency key, and this design salts it with a fresh `at` so the same delivery can never hash the same, then bolts on a seen-set to fake the identity it just destroyed — while `Coverage`, the only fact that says whether the bytes were signed, is stripped off at the one door that leaves the process.

**Producer first:** Three checks are in this design. Two of their producers are ours and can be deleted, so those checks are the wrong shape.

- Duplicate admission, or a 5xx that makes Slack (3s) and Teams (15s) retry until the heat death of the socket. The trigger is a resend, a Redeliver, a restart. The producer is `encodeRelayedEvent` in the docking-station contract: it writes `at` into the body, and DESIGN.md's Replay section defines the entry id as sha256 of `<kind>\n<previous>\n<body>`. A new clock reading is a new id. Delete that producer: the recorded body is a pure function of the verified bytes, and `previous` stays the constant `-` that `record_event.dart` already sends. `AlreadyRecorded` then makes a second entry impossible. The in-memory `ReplayKey` set becomes unnecessary for exact resends. Shipping the set while `at` remains is the defect.
- A captured GitHub delivery becomes a real action, or an unsigned header decides whether a signed body is kept. The trigger is replay. The producer is `gate()` in `webhook_gate.dart`, which lets `X-GitHub-Event` choose trigger versus ignore, plus the new record-and-act path, which has no age bound. GitHub's HMAC covers the raw body and nothing else, and it covers no timestamp header. Remove the header from the decision: admit or drop only on covered bytes, and refuse a timestamp that sits inside those bytes and falls outside the window. A body-hash cache does not make a stale first acceptance impossible.
- A captured Bot Connector token admits a message or a card verdict as any `from`, in any conversation on that `serviceUrl`, until `exp`. The trigger is token capture, and it is external. The bytes themselves cannot be refused away: `teams_gate.dart` is right that a card submission exists only in this request. The JWT check stays for that reason. The producer of *treating the body as a verified actor* is ours: the same `encodeRelayedEvent` shape used for a body-signed Slack or GitHub delivery, which `teamsRecordedEvent` then re-reads with the checks switched off. That producer can be removed. It is the second flaw, and another cache will not remove it.

**Fatal flaws:**
- DESIGN.md Replay / Proposal. Exact-resend identity and the id formula disagree. The id swallows `previous` and the whole body. "Duplicate forever, across restarts and across every relay" is true only when every writer uses the same `previous` and a body that does not contain a freshly minted `at`. Today's Teams writer sends `-`, and each entry "starts its own chain," so the claim happens to hold if `at` leaves the hash. The moment a relay writes the chain tip as `previous` — the natural "fix" once someone wants the hash chain to be the order translators walk — one resend becomes a new id, `AlreadyRecorded` never fires, and Slack's three-second retry records a second event. The interim seen-set is forgotten on restart and on 5xx, which is the overlap of a deploy and Teams' fifteen-second retry: the ninth strike is an empty map, and the logbook, still salted with `at`, will not catch what the map forgot. Webhook_gate already refused a guard that reads as covering a thing it does not. This set is that guard.
- DESIGN.md "the recorded entry is the same either way" and "what may be built on it, which is the replay section's business." `Coverage` is a Dart enum that dies at `encodeRelayedEvent`. The durable fact is `{"at","bytes"}` or bare bytes, identical for `bodySigned` and `senderOnly`. `teamsRecordedEvent` trusts the body because it was recorded, and re-reads `from`, the card `value`, and the conversation with the token checks gone. `serviceurl` binds a connector base, not a conversation and not an actor. A holder of one token forges an approval as anyone, anywhere that connector reaches. Filing that under replay under-counts it: the blast is admission. An unsigned `ReplayKey` (conversation, type, activity id, timestamp) makes it worse. Distinct bodies that share a key collapse to one winner, and the winner is whoever recorded first. The attacker who can see the honest activity id writes the forged value, the relay answers the true resend as already seen, and downstream "dedupe by the source's key" keeps the forgery. That is a mutex, and the mutex is the attack. "No weaker than the token" is the hum you were told to ignore.
- `webhook_gate.dart`, "THE CONDITION THAT FLIPS," together with DESIGN.md steps 4 and the `bodySigned` key, and open question 3. The old gate accepted replay because the action was an idempotent refresh and the unsigned event header could not escalate. Recording the body so something acts on it is that flip, and the design leaves it as an open question while specifying the record path anyway. Two consequences follow from the same uncovered header. There is no signed time, so accept-once still performs every historical captured webhook once — the seen-set only blocks the second play. And `X-GitHub-Event` is the admit/drop switch outside the HMAC: any captured body can be forced into `<source>-event` by labelling it with a wake type, or, if quiet deliveries later take the same key the way `slack_gate.dart` stores a digest on ignore, labelled `ping` first so the real `issues` delivery finds the body already seen and is dropped. Slack is safe here because the event kind sits inside `v0:timestamp:body`. GitHub is not Slack with a different header name. Open question 4's early Slack timestamp refuse does not generalize: that timestamp is bound again when the body is signed.
- DESIGN.md open question 2, still open, is load-bearing for Teams. If resends are byte-identical, the logbook hash covers them and the unsigned activity key should not exist in the relay. If they are not, exact-byte identity never collapses them, and the key `teams_gate.dart` widened on 16 November (a delete 18s after an edit was dropped when the id was the whole key) is an unmeasured guess about honest retries. A shared relay cannot ship on that shrug.

**What holds:**
- The order refuse → read → check → record → answer, with the logbook as the only way out. Killing `/ws` and `onEvent` removes a second consumer that could act before the record exists.
- `_refuseUnread` via `detachSocket`. `dart:io`'s `response.close()` would drink the body anyway; the door refusal is real.
- One deadline for the whole body, so a trickle cannot sit between chunks. Fail-closed on an empty secret or empty bot app id. `AlreadyRecorded` answered 2xx, so a true duplicate ends the retry instead of feeding it. That part of the old Teams client was the right diagnosis.
- `VerifiedDelivery`'s private constructor: inside this process, recording unchecked bytes does not compile. Slack's five-minute window sits inside the HMAC, so a body-hash there really does collapse retries whose signatures change. Teams pins RS256 and rejects `alg` games. The log line is status and reason, never the person's words.

**If RECAST, what to fold back:**
- DESIGN.md Replay: delete the in-memory `ReplayKey` set as the mechanism. Idempotency is the logbook id. State the two invariants that make the sentence "duplicate forever" true: every relay writes `previous` as `-`, and the entry body is a canonical function of the verified bytes with no `at` and no other field the relay mints per request. Docking-station agreement to drop `at` is a precondition of recording through `is_relay`, not a licence to ship the cache in the meantime. Say in the same paragraph that writing the chain tip as `previous` splits one delivery into many ids.
- Move `Coverage` out of the replay section and into the recorded entry and the translator contract. A `senderOnly` entry must be a different durable fact from a `bodySigned` one, so a consumer that wants a signed act cannot read it by accident. `teamsRecordedEvent` and `TranslatesRelayedEvents` do not treat body `from`, card values, or invoke payloads as a verified actor. The bytes may still be stored — they exist nowhere else — but they are testimony of a token holder, not of the person named in the JSON. The relay does not dedupe distinct Teams bodies by the unsigned activity key; that rule is what lets the first writer displace the honest submit.
- GitHub: the wake/quiet switch reads covered bytes only. Record every HMAC-valid body, or classify from the body, and let the translator parse. Refuse when a timestamp inside the signed body is outside the window, before the write. State plainly that a body hash with no covered time still acts once on every old capture. Do not attach `X-GitHub-Event` to the stored entry as if the signature had reached it.
- Close open question 2 by measurement before Teams joins this record path. If resends match byte for byte, Teams exact retries are the logbook's job. If they do not, write the delta down and design that delta; do not inherit the seen key from `teams_gate.dart` as folklore.
- Step 6: the source deadline is a budget that read and write must sum under. Slack's three seconds is the tight bound; a ten-second body timeout plus a ten-second logbook timeout, copied from the Teams relay, guarantees the retry this whole design is trying to absorb.

## NoetherNullPointer's Design Strike

**Verdict:** RECAST

**Summary:** The design conserves “same bytes means same event” for Slack and Teams, but not for GitHub: it drops the event kind and has no durable dedupe key, so the replay and parse invariants break on restart and on header-based sources.

**Producer first:**
- **Resource exhaustion from unauthenticated/slow senders:** producer is the relay reading the body before checking headers. Removed by ordering: header check first, cap, deadline. The design does this.
- **Recording unverified bytes:** producer is a code path that records arbitrary bytes. Removed by type: recording takes only `VerifiedDelivery`. The design does this.
- **Replay protection on unsigned Teams bodies:** producer is Bot Framework (external, cannot be removed). `Coverage` documents it. The design does this.
- **Duplicate recording from exact resends:** producer is `at` in the logbook entry, which makes identical bytes produce a different entry id. Can be removed by recording only the verified bytes (no `at`) so the logbook’s `AlreadyRecorded` catches exact resends. The design proposes this but makes it conditional and falls back to an in-memory seen set lost on restart and 5xx. This is a defect: make duplicate recording impossible by dropping `at` for `bodySigned` sources; then the in-memory seen set for them becomes unnecessary.
- **Downstream cannot parse header-based events:** producer is the recording step dropping the event kind for sources whose event kind is in a header (GitHub). Can be removed by recording the event kind, or by constraining the wake set to one type. This is a defect.
- **GitHub replay/dedupe:** producer is the lack of a unique source key in the GitHub body combined with keeping `at`. Can be removed by dropping `at` (body-hash dedupe) or by defining a durable source key. The design leaves this as an open question. This is a defect.

**Fatal flaws:**
- **Broken invariant: every logbook entry contains what its translator needs.** The design records only `{at, bytes}` (`encodeRelayedEvent`) and the source’s `VerifiedDelivery` carries no event kind into the entry. For Slack and Teams the event type is in the body. For GitHub the event type is in the `x-github-event` header (`webhook_gate.dart`’s `SourceSpec.eventHeader`). The downstream GitHub translator reads only the logbook bytes and cannot tell an `issues` event from a `ping` or any other wake event. The design’s “Not in is_relay” says parsing belongs to the source package, but the source package cannot parse without the event kind. The relay must either record the event kind, or constrain GitHub’s `wakeEvents` to a single type and document that the translator assumes it. The design does neither.
- **Broken invariant: exact resends are the only duplicates.** The replay section assumes every source has a unique source key in the body that downstream can dedupe by. Slack has `event_id`, Teams has activity id, but GitHub’s body does not contain the `X-GitHub-Delivery` id; that id is an unsigned header. With `{at, bytes}`, an exact resend after a restart gets a new `at`, so the logbook does not return `AlreadyRecorded`; the in-memory seen set is gone; downstream sees two entries with identical bytes and no source key to dedupe. If `at` is dropped, the logbook dedupes by body hash, but then two distinct GitHub events with identical bodies are conflated and one is lost. The design leaves this as open question 3 rather than resolving it.
- **The in-memory seen set is a correctness mechanism for duplicates, but it is not durable.** The design says “A seen set is forgotten on restart and on a 5xx, so a duplicate can still be recorded twice. Downstream dedupes by the source’s key.” That holds for Slack and Teams, but not for GitHub. The producer is the `at` field plus the lack of a durable dedupe key. The fix is to remove the producer: record only verified bytes for `bodySigned` sources so `AlreadyRecorded` handles exact resends across restarts; for `senderOnly` sources, keep the activity key and rely on downstream dedupe, documenting that the seen set is only an optimization. The design’s conditional “until the docking station agrees” leaves the GitHub relay unsound.
- **`Coverage` is not persisted, so downstream cannot know the trust level of a recorded body.** The design records the same entry for `bodySigned` and `senderOnly`. For Teams, downstream can infer by source. But if a source ever has mixed coverage or a new source uses `senderOnly`, the logbook entry does not say. The replay section uses `Coverage` only within the relay. If downstream acts on the bytes, it may need to know whether they were body-signed. This is a coupling that should be removed: either record `Coverage` in the entry, or explicitly state that downstream can infer it from the source and that it never changes for a source.

**What holds:**
- The type-level `VerifiedDelivery` and private constructor prevent recording bytes that never passed a source check.
- The order of operations (refuse, read under cap/deadline, check, filter, record, answer) is sound for sources whose event kind is in the body.
- `AlreadyRecorded` as 2xx is correct; it stops infinite retries.
- `Coverage` correctly documents that Teams tokens vouch for sender, not body, and that no relay can fix that protocol limitation.
- Fail-closed configuration (missing secret or bot app id refuses everything) is the right invariant.
- The `_refuseUnread` technique avoids waiting for the body on refusals that can be decided from headers.
- The `ReplayKey` for `bodySigned` (body hash) correctly catches Slack retries that change the signature.

**If RECAST, what to fold back:**
- Specify how the event kind is recorded for sources whose event kind is in a header (GitHub). Either extend `encodeRelayedEvent`/`RelayedEvent` to carry a source event kind, or require the source’s `VerifiedDelivery` to carry it and record it, or constrain GitHub’s `wakeEvents` to a single event type and document that the translator assumes it. The docking station format change may be needed.
- Make dropping `at` a requirement for `bodySigned` sources (GitHub, Slack) before building the relay, or provide a durable dedupe key. Do not rely on an in-memory seen set for correctness across restarts.
